# 定时任务批调度简报

2026-11-24 · 设计草案 · 以新版批调度看板和 Scheduler 领域口径为依据

## 特性名

定时任务批调度简报

## 定位

来源系统的值班人员和任务运营人员在指定时间通过招乎收到当天各批次的名称、状态、进度和子任务级失败统计，同时查看各共享模型池的 Worker 容量和当前占用。调度平台维护发送时间，回调传入来源和收件人。Monitor 从新版批调度看板和异步子任务的数据源生成统计快照，Scheduler 组织发送和追踪，SWE 通过现有招乎渠道投递。

## 工作内容

### 1. 统计范围和时间

- 按单个 `source_id` 统计已关注父任务的新版批调度，关注以取数时状态为准。批次来源为 `swe_cron_managed_trigger_receipts` 中已受理、`kind=batch` 且有 `batch_id` 的回执，包含自动触发及手动触发整批。招乎批次总数和批次列表使用同一范围，排除整批触发被跳过、无入队成员以及所有入队成员均为 `skipped` 的批次。一个批次只有部分成员跳过时仍纳入报告。独立运行的普通任务、单任务立即执行和旧版批次在范围之外。 [批调度任务关注](../superpowers/specs/2026-11-25-cron-batch-follow-design.md)
- 以 Scheduler 受理请求时的北京时间日期确定业务日。批次按 `logical_fire_at` 归属，取该日 00:00 至次日 00:00 的左闭右开区间，且计划时刻已到统计快照时间。提前触发或跨日继续执行的批次归原计划业务日。需要跨日看积压时可在看板调整日期范围。
- 每次报告按实际取数时刻观察成员状态，记录受理时间和实际取数时间。后台取数即使跨日，仍沿用该请求受理时确定的业务日。
- 每次调用生成一份快照，所有收件人共享该份内容。同一天后续调用重新取数。

### 2. 逐批次状态、进度和失败统计

| 指标 | 统计规则 |
| --- | --- |
| 名称和状态 | 每个有可报告执行的批次展示父任务名称、计划时刻和状态。缺少名称时显示「未命名任务」。状态沿用新版看板的已完成、已失败、运行中、待处理。运行中优先于待处理，批内成员全部结束后才按有无失败归为已失败或已完成。已完成和已失败的批次有结束时刻时按北京时间显示，与计划时刻跨日时带完整日期。 |
| 批次进度 | 展示已结束成员数 / 实际入队成员数及百分比，同时拆出成功、失败、跳过或取消、运行中、待处理。已结束 = 成功 + 失败 + 跳过或取消。运行中包含派发中、已受理、实际运行和主执行成功后等待结算。待处理包含排队和派发未确认。 |
| 失败详情 | 有失败成员时，展示主任务失败数和子任务失败数，均按成员计数。主执行失败计入主任务失败，主执行成功但异步结算失败计入子任务失败，包括异步等待超时。同一成员只计一次。失败成员数为零时省略失败详情。 |
| 子任务失败类型 | 在子任务失败数后的括号中列出各类型及数量，单行超长时分行展示。类型复用看板当前执行历史，一个成员涉及多个类型时按组合归类，例如「API + Prompt 2」表示有两个成员属于这个组合。异步等待超时显示「超时」，缺少类型时显示「未记录类型」。 |

- 按批次成员关系读取 `current_execution_id` 指向的当前尝试。重试沿用原批次和成员身份，下一份报告反映最新进度。实际被批次复用的普通执行计入其所属批次。入队前跳过保留在回执，进度分母以实际登记成员为准。
- 子任务错误类型按“批次成员 → 当前执行 → `history_execution_id` → 经执行身份校验的 `swe_cron_executions.error_type`”关联。仍等待结算的成员保留运行中状态，其子任务异常在成员结算失败时纳入失败明细。
- 筛选后没有可报告批次时，消息显示「截至当前暂无可报告的关注批次」，同时展示全来源共享模型池。取数失败按报告任务策略恢复。关联缺失时标注对应批次数据不可用，或标注失败分类暂不可用。

### 3. 模型 Worker 容量和当前占用

- 按 `source_id + provider_id + model_id` 展示每个共享模型池。容量读取最新发布的 `effective_workers`，并保留发布时间。存在当前占用或已配置模型策略但尚未发布容量时，显示“容量未发布”。
- 当前占用按共享模型池的实时在途记录计数，覆盖已领取且未释放的旧、新批任务，包含主执行结束后仍在等待结算的 Worker。排队、直接派发且无需共享名额的执行，以及已释放名额的执行在此口径之外。取数使用实际在途记录，历史容量调整记录中的 `running_count` 仅代表当时样本。
- 模型池区域显示“已占用 / 有效容量”。每个批次再按成员的实际执行模型列出本批占用，支持同批跨模型。模型池总占用可包含简报时间窗口以外的批任务，各批占用按与池总数相同的占位口径关联。

### 4. 招乎消息格式

先单独发送一条汇总，包括来源、业务日、取数时刻、批次概况和共享模型池。随后发送逐批次进度与失败统计，按计划时刻和 `batch_id` 稳定排序。招乎正文的逐批明细仅展示任务名称和计划时刻供识别。

```text
【定时任务批调度简报】RMASSIST
业务日 2026-11-24 · 取数 2026-11-24 12:00（北京时间）

关注批次共 2 个 · 已完成 1 · 运行中 1

全来源共享模型池 · 当前占用 / 有效容量
供应商 A / 模型 A   7 / 10
供应商 B / 模型 B   2 / 4
```

```text
【定时任务批调度简报】RMASSIST
业务日 2026-11-24 · 取数 2026-11-24 12:00（北京时间）
明细 · 第 1/1 段

09:00 · 客户名单生成 · 已完成 · 结束 09:26
进度 20/20（100%） · 成功 20 · 失败 0
本批 Worker 占用 0

11:00 · 客户跟进计划 · 运行中
进度 18/24（75%） · 成功 16 · 失败 2 · 运行中 4 · 待处理 2
本批 Worker 占用 · 模型 A 3 · 模型 B 1
主任务失败 1 · 子任务失败 1（API + Prompt 1）

```

- 明细列出筛选后的所有批次及各批失败统计。达到单条消息上限时按批次分段，明细带“第 X/Y 段”。超限的模型池列表随明细续发。没有可报告批次且模型池能放进汇总时，只发送汇总。
- 招乎消息保存发送时点的快照内容。

### 5. 平台回调和职责分工

调度平台直连 Scheduler。Scheduler 经 SWE 向 Monitor 取数，再调用 SWE 招乎发送并记录结果。平台作业由运维注册并维护，比如同一来源在 12:00 和 18:00 分别发送给值班人员和运营人员。

`POST /api/scheduler/cron/batch-status-reports` 沿用可信内网直连方式。收件人使用招乎通道可解析的员工号，按字符串校验和去重。

```json
{
  "source_id": "RMASSIST",
  "recipient_ids": ["00001234", "00005678"]
}
```

- 平台只传来源和收件人，可使用固定请求体。Scheduler 受理时生成 `report_id`，平台配置的触发时间决定调用时点。
- Scheduler 校验请求后持久化受理，返回 HTTP 202 和 `report_id`。后台生成快照并逐人投递，报告及逐人状态可按 `report_id` 和 `source_id` 查询，供运维核对。
- Monitor 采用 `monitor/src/monitor/app/services/cron/managed_board_sql.py` 的批次关联和状态归约，按简报范围筛选批次，批量关联实际异步子任务并按批次聚合。模型池取数沿用同目录的 `managed_board_workers.py` 和 `managed_board_occupancy.py`。从同一数据库读视图取数，报告快照只需要各批状态、进度、失败计数和模型池数据。简报取数走受控服务入口。
- SWE 读取来源默认 Agent 的现有招乎渠道，复用 `src/swe/app/channels/zhaohu/channel.py` 的地址解析和推送协议。发送结果以渠道业务返回码判定，渠道确认受理记录为“已发送”。
- 可参考 `docs/integrations/cron-daily-failure-rerun.md` 的外部平台注册、HTTP 202 与后台处理方式。简报使用独立快照和投递记录，走直接的服务调用链路。

### 6. 去重、恢复和验收

- 每次受理生成独立报告，即使请求体相同。取数完成后一并保存报告快照、消息分段和投递任务。投递按 `(report_id, recipient_id, part_no)` 唯一，尚未尝试的投递照常推进。
- 每位收件人的每段消息只尝试发送一次。发送前持久登记已开始投递，发送后保存已发送、失败或结果未知及可用的渠道回执。明确失败和结果未知均作为该分段的最终记录，不重试。发送超时或开始投递后进程中断且无明确结果时，记为结果未知。所有消息段均获渠道受理时，收件人记为已发送。部分受理时显示已发送段数及其余分段的状态。
- 验收覆盖同来源同窗口下可报告批次数和进度与新版看板对数、同名批次、整批跳过、部分成员跳过、全量分段和两层失败计数。模型池验证同批跨模型、新旧队列共享、待结算仍占位、纯文本直接派发及容量未发布。投递验证平台固定请求体直连、同日多次调用、受理跨日、查询来源匹配、并发领取和失败后单次投递。使用测试作业验证渠道消息长度、员工号解析和返回码。
