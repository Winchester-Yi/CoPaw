# 旧版定时任务勾选迁移与聊天页最小兼容

## Summary

在旧版定时任务管理页支持勾选批量迁移，以完整父子组异步迁入 Scheduler，保留任务 ID 和原聊天、会话绑定。聊天页在同一次交付中完成最小兼容：已成功迁移的任务只展示新版，未迁移的继续展示旧版，原生新版任务继续正常展示。

本文记录已确认需求和设计约束，不代表功能已经实现；后端兼容问题中尚未定案的部分单独列出，不擅自变更旧接口、旧数据或全局双写策略。

---

## Problem Frame

旧任务仍存在于文件和旧管理链路中，新版已有独立管理、执行及查询能力。用户需要从旧页面选择任务迁入新版，同时延续原会话和可恢复状态，而不是另建一套任务身份。

当前聊天页将新旧列表直接拼接，任务键包含来源，且会话定位要求只能匹配一个任务。同一个任务迁入后，旧记录仍在，因此仅保留 ID 并不能避免重复入口和归属冲突。旧表记录虽然存在，新版管理操作的旧表投影校验也不一定接受旧记录。

---

## Actors

- A1. 有任务管理权限的用户：选择任务、确认迁移范围、查询进度及重试失败组。
- A2. Console：提供旧页迁移入口及聊天页来源选择，不擅自扩大权限或重新创建会话。
- A3. Scheduler：接管新版定义、管理状态及新平台绑定，提供可靠的迁移结果与新版任务信息。
- A4. SWE：提供可恢复的旧定义、状态及原会话资源信息；旧执行链路继续按原行为运行。

---

## Key Flows

- F1. 勾选并迁移
  - **Trigger:** A1 在旧管理页勾选任务并确认。
  - **Actors:** A1、A2、A3、A4。
  - **Steps:** 校验管理权限；展开父任务的全部分发子任务并展示实际数量；后台采集快照；准备新版记录和新平台入口；整组准备完成后按继承状态开放新版入口并确认迁移结果。
  - **Outcome:** 成功组保留原身份并由新版管理；失败组保留进度，其他组继续。
  - **Covered by:** R1–R12。
- F2. 迁移后打开原会话
  - **Trigger:** 用户刷新聊天页、点击任务，或通过任务/会话链接进入。
  - **Actors:** A1、A2、A3。
  - **Steps:** 获取当前身份下的任务及可信迁移归属；统一选择任务来源；已迁移条目仅采用新版；导航到原聊天/会话；按选定来源查询状态、执行已读等操作。
  - **Outcome:** 同一任务只有一个可操作入口，不因同时存在旧记录而变成无法定位的任务。
  - **Covered by:** R3、R13–R18。
- F3. 失败重试与刷新
  - **Trigger:** 某组失败、用户关闭后重开页面，或一次查询失败。
  - **Actors:** A1、A2、A3。
  - **Steps:** 查询已保存进度；区分未完成和已迁移；重试未完成步骤；保留已确认成功的操作；恢复查询后按最终归属刷新聊天列表。
  - **Outcome:** 不误报成功、不重复执行已确认成功的平台注册，也不把查询失败解释成“应回退旧任务”。
  - **Covered by:** R9–R12、R17。

## Requirements

**选择、身份与权限**

- R1. 旧管理页增加勾选批量迁移能力，沿用原页面样式；仅增加选择、确认及进度所需界面，不重做旧管理页。
- R2. 沿用现有任务管理权限。父任务必须连同全部分发子任务整组迁移，子任务不能单独迁移；确认前展示自动纳入后的实际父、子任务数量。无分发子任务的任务独立处理。
- R3. 保留每个任务原 `job_id`、`task_chat_id` 和 `task_session_id`；比较及关联使用 tenant、source、Agent、job ID 的完整身份，不凭裸 ID 跨用户或跨来源接管。无法确认原绑定时不得生成新 ID 冒充保留成功。

**数据和调度行为**

- R4. 迁移任务配置及可恢复的未读次数、自动暂停信息、最近执行时间、结果摘要和错误信息。已有历史记录继续沿用，不因迁移复制历史或创建第二份会话。
- R5. 继承原任务启停状态以及普通调度、开启批调度、暂停批调度的三态；暂停任务不能因迁移被打开。
- R6. 迁移后的任务默认非工作日不执行，保留原 Cron 表达式并按新版日历过滤；这可能改变原来每日执行任务的节假日行为。
- R7. 迁移链路的初始化、平台注册、启用及重试不写 `swe_cron_jobs`，不修改旧 `jobs.json`，不停用或删除旧平台定时器。任务定义写新版定义表、状态及原会话绑定写新版状态表，另保存必要的注册、批控制和迁移进度记录；新平台 ID 只保存到新版绑定，不覆盖旧绑定。
- R8. 允许迁移运行中、等待异步结果或已入队的任务，不取消、不接管旧执行，不追踪补同步旧执行后续状态。旧在途状态留在迁移记录，新版运行状态初始化为空闲；未读、暂停和历史结果仍保留，已结束任务保留原结果状态。
- R9. 新表中同身份的旧快照可以继续迁移接管；已经确认迁移完成的 Scheduler 任务跳过、不覆盖、不重复注册。绑定或父子关系冲突时明确失败。上次迁移留下的未完成记录不能仅因已经入新表就被误判为“已迁移”。

**进度、失败与发布**

- R10. 异步后台执行，页面可查看进度、各组成功/失败情况和原因，关闭页面后可重新查询。尚未约定服务重启后的自动续跑策略，不能把“进度可查”写成“自动恢复执行”。
- R11. 各父子组独立推进，失败不阻止其他组。保留已完成步骤，重试只补未完成部分，已确认成功的平台注册不重复执行；不自动回滚成功组。
- R12. 整组准备完成后，才按原启停状态和模式开放本次准备的新版入口；准备中或失败的组不能提前投入新版调度。整组成功后才发布本次迁移完成事实；不干预此前已成功迁移、此次仅跳过的任务。

**聊天页最小兼容——本次新增确认范围**

- R13. 已成功迁移的任务只展示新版入口，未迁移的继续展示旧版，原生新版任务正常保留。只消除同一完整任务身份的旧/新版双份，不按名称或裸任务 ID 合并，也不重做页面样式和其他排序规则。
- R14. “已迁移”必须依据服务端可验证的接管完成事实，不是“新表有一行”或某次列表中出现了相同 ID。仅旧快照、迁移准备中、失败未完成的任务仍按旧来源展示；本次未完成的新记录不能形成第二条聊天任务入口。
- R15. 任务点击、任务 ID 链接、会话 ID 链接、当前任务定位和选中态使用同一来源选择结果。复用原聊天/会话，不能只把侧栏重复项藏起来，却仍让详情定位得到两个任务并返回空值。
- R16. 最近执行状态、下次运行时间、未读计数和已有任务操作均取自选定来源；已迁移任务的自动/手动已读及报告已读等操作走新版，未迁移任务走旧版。不能展示新版状态却回写旧管理接口，也不能混拼两份任务状态。
- R17. 接口失败、超时、分页不完整或新版列表暂时没有返回，不能据此判为未迁移。已确认的新归属保留，必要时只读展示已知信息并提示暂不可用；无可靠归属时不得自动尝试旧写接口。已迁移后在新版删除/隐藏的任务不得因旧记录仍在而重新显示为旧任务。用户、来源或 Agent 切换后隔离先前缓存和异步回包。
- R18. 归属判断仍须核对原绑定；同身份但绑定冲突、或不同任务偶然共用会话时，明确提示冲突，不强行合并、不任意选择接口、不补建新会话。聊天去重不等于调度去重，也不解决两个调度入口同时执行的问题。

### 聊天页来源选择

| 观察到的情况 | 展示与操作归属 |
|---|---|
| 已确认未迁移，只有旧任务 | 展示旧任务，原旧操作继续 |
| 同身份两份任务，且迁移已成功、绑定一致 | 仅展示新版，打开原会话，使用新版状态和操作 |
| 新表只有旧快照，尚未接管 | 继续展示旧版，不能把快照当成新版任务 |
| 迁移准备中或失败，尚未完成 | 继续展示旧版；进度在迁移界面查看，不产生第二个聊天任务入口 |
| 原生新版任务，没有旧副本 | 沿用现有新版行为 |
| 已确认迁移，但新版查询暂时失败 | 不退回旧来源；保留已知新版信息并提示不可用，不能发起旧写操作 |
| 已迁移任务已在新版删除/隐藏，旧副本仍在 | 按新版可见性处理，不让旧副本重新出现 |
| 完整身份或绑定无法可靠确认 | 提示归属/绑定异常，不盲目合并或写入 |

R14、R17、R18 是“已迁移只展示新版”的必要一致性约束，不增加旧入口停用、历史复制或新会话创建功能。

## Acceptance Examples

- AE1. **Covers R1, R2, R10.** 勾选一个父任务，关联三个分发子任务，确认页显示四个实际迁移成员；直接选择子任务不能单独提交。无权限操作被拒绝，且不能通过修改请求扩大范围。
- AE2. **Covers R3, R4, R7.** 迁移前后四维任务身份、聊天 ID、会话 ID 完全相同，未读及已有结果按快照保留；无新增会话或复制历史，迁移路径没有对旧定义表、旧任务文件或旧平台入口的写操作。
- AE3. **Covers R5, R6, R12.** 原任务为暂停批调度，迁移后仍暂停批调度且默认过滤非工作日；不能为了完成迁移把它临时启用。整组就绪前，新入口不执行业务。
- AE4. **Covers R4, R8.** 旧任务正在执行且未读为7，允许迁移；新版未读仍为7、运行状态为空闲，旧在途状态仅记录快照。旧执行稍后完成，不伪造一次新版执行或补写新版计数。
- AE5. **Covers R9.** 目标是可信旧快照时继续接管；已经迁移成功的同身份任务重提时跳过；父子关系或绑定不一致则失败，不能覆盖别的任务。
- AE6. **Covers R10, R11, R12.** A组成功、B组某步失败、C组仍继续；重开页面可以查询结果，重试B组不重复做已确认成功的平台注册，B组未就绪前不作为迁移成功发布。
- AE7. **Covers R13, R14, R15.** 同一个任务在两个列表中均存在且已迁移成功，聊天页只有一个入口；两份旧/新记录仍在后台，但任务链接和会话链接都能定位到同一个原会话，不出现归属不唯一。
- AE8. **Covers R13, R14.** 同页包含未迁移A、已迁移B、迁移失败C和原生新版D：A/C采用旧来源，B/D采用新版；B与C均不能出现旧新双条目。
- AE9. **Covers R15, R16.** 打开已迁移任务后，自动已读及报告已读请求使用新版归属；未迁移任务继续调用旧接口。展示的未读、最近运行和可操作状态与请求来源一致。
- AE10. **Covers R17.** 新版接口超时而旧列表成功，已确认迁入的任务不能重新变成旧任务或尝试旧已读；新任务被删除而旧副本仍返回时，旧副本不复活。切换来源时，旧请求迟到不能改变新来源列表。
- AE11. **Covers R3, R18.** 两个来源恰好使用相同 job ID，不能合并；同身份却聊天/会话绑定不同不能静默择一；不同 job ID 共用聊天也不能套用迁移去重规则。

## Success Criteria

- 用户能从旧页完成有权限的批量迁移、核对父子范围、回查和续办失败组。
- 成功迁移不改变任务/会话身份，不新增重复会话，迁移过程不回写旧定义表或干预旧入口。
- 聊天页对已迁移、未迁移和原生新版任务给出唯一且一致的入口、状态和操作归属。
- 查询错误、部分迁移和新版删除不会触发旧来源误回退。
- 后续开发可区分已确认行为与下列未定兼容策略，不能把“导入新表成功”当作全部生命周期验收完成。

---

## Scope Boundaries

- 本次新增聊天页最小兼容，替代此前“聊天页留到以后切入口”的决定；不是将聊天页全部切成只查新接口。
- 不停用、删除旧平台入口，不关闭旧管理接口，不修改旧任务文件；旧入口由用户另行处理。
- 不接管旧在途执行，不复制历史，不新建第二份会话，不进行全来源/全用户自动扫描迁移。
- 不全局取消原生新版任务的旧表同步，不迁移全部 Monitor 旧读方；迁入任务后续投影规则见未定事项。
- 不拆共享模型池、不删除 CronManager 或整套旧代码，不重做聊天页布局和无关交互。
- 用户已于2026-11-05授权开发；本地实现及测试不等于获准执行行内迁移，不自动提交、推送或打包。

---

## Key Decisions

- 身份延续而非复制：历史和聊天资源继续使用原绑定，平台定时器是新建对象，不能把平台 ID 与业务任务 ID 混为一谈。
- 以迁移完成事实决定聊天归属：新表存在、记录可见、任务已迁移成功不是同一件事；列表隐藏不代表迁移归属消失。
- 统一选择来源再展示和操作：仅过滤侧栏不足以修复任务/会话定位、已读及选中态。
- 允许在途迁移但不接管旧运行：保存业务快照，不把旧 running/queued 伪造成新版的在途执行。
- 新旧暂时共存：本次聊天兼容只解决入口与归属；旧新定时器同时启用仍可能重复执行和向同一会话追加结果。

---

## Dependencies / Assumptions

- 用户确认旧任务在 `swe_cron_jobs` 中已有记录。记录存在不代表所有字段完整或已满足新版投影归属校验，应只读核验，不能默默修写旧表。
- 需能取得完整父子身份和可恢复状态；文件与各实例内存不具有统一原子快照。状态采集范围及缺失表达需在详细设计中明确，不能用默认空状态冒充完整快照。
- 外部平台已确认的注册成功可复用；丢失响应不能假定平台提供查询接口，也不能承诺未知注册结果绝不会产生重复记录。
- 共享原会话资源使新旧操作存在相互影响，保留相同 ID 不等于资源隔离。

## 已核对的代码约束

以下是基于 `c71f4d4d9` 的分析，不是已实施的修复：

- `console/src/api/modules/cronTaskSources.ts` 的 `mergeTaskSources` 直接拼接新旧任务，`taskIdentityKey` 将来源计入键；`resolveTaskOrigin` 遇到两份同 ID 详情会报归属不唯一。
- `console/src/pages/Chat/taskJobs.ts` 的任务 ID/聊天 ID 定位都要求唯一匹配；`useChatTaskSources.ts` 负责双查和缓存。因此需要统一来源选择，不是只隐藏重复DOM节点。
- `scheduler/src/scheduler/app/services/cron/managed/projection.py` 仍要求旧记录标记为 Scheduler 管理；控制、删除、模式切换及日期维护会调用该投影。仅在导入步骤跳过写入，并不能避免迁移后的操作回滚。
- `scheduler/src/scheduler/app/services/cron/managed/controls.py` 的历史已读范围依赖新版执行关联；仅复制未读计数，不能自动关联迁移前旧历史。
- `src/swe/app/crons/managed_resources.py` 的普通准备/清理流程假定新版资源归属，不能未经适配就接管并清理原会话；旧删除流程也会清理共享聊天资源。
- 既有[第一阶段快照迁移](../superpowers/specs/2026-10-15-cron-phase1-snapshot-migration.md)只保存 legacy 快照，不等于本设计的 Scheduler 接管流程；不能直接恢复旧路由就宣称完成本次功能。

## Outstanding Questions

### 2026-11-05 开发前确认

- [Affects R7, R16] 仅服务端确认的迁入任务豁免旧表投影，覆盖后续管理操作；原生新版任务保留现有双写，不能凭客户端提交的元数据绕过归属校验。
- [Affects R3, R4, R18] 用户选择保留原会话资源：新版删除迁入任务时删除新版任务、关闭新版入口，但保留原聊天、归档及相关资源。旧删除接口不改，仍需避免从旧页面删除迁入任务。

### Deferred to Planning

- [Affects R9–R17][Technical] 明确服务端迁移完成事实、完整身份和删除可见性的查询合同；保证其独立于新旧列表是否成功返回，客户端不能伪造或通过普通编辑丢失该事实。
- [Affects R3, R7, R12][Technical] 制定保持原 ID/绑定的专用接管路径及平台注册引用规则，不能套用普通创建的 ID 生成、旧 ID 冲突和资源重建逻辑。
