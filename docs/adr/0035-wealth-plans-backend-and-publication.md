# Wealth plans persist in three normalized tables and publish as one cron job per scene

The Wealth Workbench's Plan CRUD and publication loop live in a new `src/swe/app/wealth_plans/` module (the existing `src/swe/app/plans/` is the unrelated chat Plan-Mode feature) exposing `/api/wealth/plans*`. Plan data is stored in three MySQL tables — `swe_wealth_plans` (header), `swe_wealth_plan_scenes` (one row per selected scene), `swe_wealth_plan_targets` (one row per Distribution Target) — because JSON columns are not allowed by the database convention here, and the normalized targets table is what makes the board's "plans I created OR plans distributed to me" query an indexed lookup instead of a full scan. Publication is asynchronous: the create/update endpoint persists the plan with `status=publishing` and returns immediately, then a background task creates one cron job **per scene** (each scene carries its own `cron_expr`, skillId and schedule, so a single job per plan cannot express it), broadcasts each job to the targets by reusing the existing cron-broadcast machinery (`_schedule_broadcast_task` / `swe_cron_broadcast_tasks`), and finally writes back per-scene `cron_job_id` / `broadcast_task_id` plus the aggregate plan status. Skill/MCP distribution to the market service (`POST /api/market/distributions`, contract in `docs/batch-distribution.md`) runs as a third publication leg in `market_dispatch.py`: one batch per publication, whose `batch_id` is `wealth-plan-{plan_id}-{content-hash}` so retries of identical content are idempotent (the market service dedupes on source+batch+content) while a modified plan republishes under a fresh batch instead of hitting 409. The header table's `skill_dispatch_task_id` stores that batch id (not a task id) with `skill_dispatch_status / skill_dispatch_error` alongside, because batch status lives in the market service and cannot be joined locally the way broadcast status can; list/detail queries refresh non-terminal batches on demand. This leg never flips the plan's overall publish status — cron jobs are already live when it runs — it only participates in the board-status aggregate. Editing a published plan updates its cron jobs and re-broadcasts; removal cascades to the jobs and their broadcast children; plans are editable/removable only by their creator (`sap_id`). Scene catalog data comes from the external `/api/agent/workspace/skill-config/list` via a backend proxy endpoint (`GET /api/wealth/scene-skills`) that falls back to built-in mock scenes when the external service is unreachable, so the frontend never talks to the external service directly.

**Consequences**

- DB schema changes require altering three tables; the no-JSON constraint is deliberate — do not "simplify" back into JSON columns.
- Deleting or editing a plan fans out to per-scene cron jobs; any change to scene structure must keep `cron_job_id` bookkeeping consistent or orphaned jobs will keep firing for distribution recipients.
- The board status column is a derived aggregate over broadcast snapshots (and later the market leg), not a stored value — stored `status` only tracks the publication lifecycle.
- The mock scene fallback lives server-side (`scene_fallback.py`); once the external skill-config service is stable, the fallback can be removed without touching the frontend contract.
- Product categories carry stable English codes (`insurance / finance / deposit / payroll / cross_border / fund`) shared by the frontend filter, the proxy request parameter, and the fallback data.
