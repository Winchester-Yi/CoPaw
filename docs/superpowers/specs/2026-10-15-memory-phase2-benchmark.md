# 第二阶段内存优化：本地合成基准记录

原始证据：[JSON](2026-10-15-memory-phase2-benchmark.json)。脚本：[benchmark_memory_phase2.py](../../../scripts/benchmark_memory_phase2.py)。

在仓库根目录运行：

```bash
env PYTHONPATH=src venv/bin/python scripts/benchmark_memory_phase2.py \
  --counts 10000 100000 \
  --output docs/superpowers/specs/2026-10-15-memory-phase2-benchmark.json
```

本次运行环境为 macOS 15.8.1 / arm64 / Python 3.12.12，本地文件系统。每个规模使用独立临时目录，测量结束即删除；2B 的十万条样本真实生成 99,936 个冷 turn、独立 reference 和分批 latest 索引，热状态为 64 条。样本正文为每条约 256 字符的合成文本。fixture 直接写文件、不逐条 fsync，构建时间和内存不计入操作测量，不能视为生产迁移耗时。

测量时使用真实追加和提交路径，包括 fsync。`tracemalloc` 只统计操作中新增的 Python 分配峰值，不代表进程 RSS；应用读写字节由 `open/read/write` 包装器计数，不含目录、inode 等元数据系统调用。目录枚举单列 `scandir_entries`。查询包含一次 session 根读取。每项只运行一次，文件刚创建，缓存较热；时间用于复核样本，不代表 NAS 延迟 SLO。没有测量旧实现，因此不报告百分比收益。

| 操作 | 历史规模 | Python 分配峰值 KiB | 应用读取 KiB | 应用写入 KiB | 耗时 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| checkpoint 追加一条 | 10,000 | 51.9 | 88.6 | 1.2 | 19.26 |
| checkpoint 追加一条 | 100,000 | 47.7 | 52.6 | 1.2 | 12.78 |
| 冷 turn 点查 | 10,000 | 95.4 | 28.2 | 0.0 | 1.20 |
| 冷 turn 点查 | 100,000 | 95.9 | 28.4 | 0.0 | 2.01 |
| 查只有冷记录的 Chat 最新 turn | 10,000 | 145.4 | 45.5 | 0.0 | 11.63 |
| 查只有冷记录的 Chat 最新 turn | 100,000 | 158.6 | 61.5 | 0.0 | 21.66 |
| 65 条热终态提交、冷移出一条 | 10,000 | 199.7 | 27.3 | 30.0 | 12.28 |
| 65 条热终态提交、冷移出一条 | 100,000 | 198.8 | 27.6 | 30.3 | 12.59 |

checkpoint 十万条 fixture 的 journal 总量为 33,088,895 字节，追加只解码当前段 160 条、读取 journal 52,961 字节；一万条样本当前段为 272 条。这解释了较大样本单次测量反而较小，不能据此推断延迟随规模下降。两个规模均未读取旧 sealed 段，也未枚举目录。

2B 点查均只枚举该 ID 的一个版本。latest 的末次候选批次分别有 16 和 32 个，所以读取正文数量及峰值不同；它没有读取全部冷正文。该样本每个 turn 只有一个冷版本，不能据此宣称多次重入、变更 Chat 后的异常回溯严格 O(1)。相关语义由故障/更新测试覆盖，最坏元数据 I/O 仍可能随历史版本数增长。

以上证据仅覆盖普通追加、点查、最新状态和一次常规提交。完整历史响应、全量校验、导出、首次迁移和大量未结算 turn 仍可能按输出或源数据规模占用内存。实际共享 NAS 上的双 Pod flock、掉电持久性、备份恢复演练和小文件元数据开销仍需在灰度启用前验证。
