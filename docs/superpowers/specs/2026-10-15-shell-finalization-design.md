# Shell 大输出最终处理分析与方案

状态更新：用户已确认并采用 [严格存储失败策略](../plans/2026-10-15-strict-shell-output-storage.md)：已启用 Unix spool 的磁盘失败不再完整读回，初始化拒绝启动、执行中终止、最终保存失败保留退出码并报错。下文的首轮兼容回退描述属于历史方案。

状态：阶段 A 已实现并验证；阶段 B 经两轮测量触发回退门槛，未交付。基线设计基于 `159cfb292`，实现对比基线为 `d2963d586`。保持完整输出、artifact 格式、截断引用、错误分类、编码回退与持久化保证。

交付结果：每流仅定位一次边界，全换行 8/64 MiB 的本机最终处理耗时约减半；普通 ASCII/非法尾字节基本持平。单遍候选的非法尾字节耗时增加约25%～101%，超过20%门槛，因此继续保留原双遍预校验。原始数据与复现方式见 [测量报告](../benchmarks/2026-10-15-shell-finalization.md)。

验证边界：已覆盖编码、marker、格式、持久化失败与取消所有权回归。256 MiB、固定时长并发、worker 排队、loop p95/p99、RSS/容器内存及 fallback 次数/字节的完整测量仍待部署环境验证，不作为本轮收益结论。

## 1. 当前路径需要准确区分

正常 Unix spool 大输出已经有界：原始 pipe 内容落到临时文件，`decode_streams` 不会 read_all 已落盘的流；`_write_response` 分块解码并生成最终 artifact，随后读取有限头尾作为展示。不能把该路径描述为结束时完整解码整个大文件到内存。

真实剩余成本：

1. `_decoded_chunks` 首先完整验证 UTF-8，再从头读取并解码输出。UTF-8 正常大文件需要两遍输入读取。
2. `_write_response` 对每条流调用两次 `_stream_bounds` 判断非空，真正写出时又算边界。大量前后换行会重复扫描。
3. 逐块解码、编码和 stderr marker 扫描仍有 CPU 成本；worker 中的 Python 工作仍可能竞争 GIL，但已有短窗口 p99 数据不能证明尖峰来自这里。
4. 最终 artifact 的 flush/fsync/replace 是持久化路径的一部分。存储延迟与 CPU 需要分开，不能通过删除 fsync 获得表面改善。
5. 首轮 spool 写入或 artifact 失败会读回完整内容，曾可能同时持有原始 bytes、解码字符串和格式化结果；该回退现已移除并改为明确存储失败。未启用压缩和 Windows 兼容路径仍可能保留完整输出。

## 2. 本轮定位探针

在当前虚拟环境中，对 8 MiB stdout、4096 字节展示预算的最终阶段做单轮 cProfile 与 `_read_chunks`、`_stream_bounds` 计数，临时目录在本机，未修改仓库实现：

| 输入 | 分块数据读取量（不含边界扫描） | 边界函数次数（含空 stderr） | 单轮总时间 |
|---|---:|---:|---:|
| 正常 UTF-8 ASCII | 16 MiB | 5 | 约 14.2 ms |
| 末尾非法 UTF-8 | 16 MiB | 5 | 约 6.0 ms |
| 全换行 | 0 | 4 | 约 28.1 ms |

正常 UTF-8 的 fsync 单次约 7.1 ms；全换行的 bytes.lstrip 累计约 26.3 ms。数据支持重复读取和换行扫描确实存在，但不能用一次探针比较三个场景的速度，也没有测出可靠的并发 p99、GIL 占用或 RSS 峰值。缓存、文件系统及探针开销都会影响结果。后续优化必须重复测量，不能把这些数值当作收益承诺。

## 3. 可选方案

| 方案 | 收益 | 代价与兼容性 |
|---|---|---|
| 缓存终态边界、保留双遍解码 | 风险小，消除重复边界扫描 | 正常大文件仍读取两遍 |
| 边界复用、乐观单遍 UTF-8，失败重写当前段（推荐分阶段） | 正常 UTF-8 一遍输入即可生成 artifact；不增加 append 热路径状态 | 非法编码尤其末尾失败时会发生部分写入回滚和重写，需评估代价 |
| append 时维护 UTF-8 验证状态 | 最终阶段不用验证扫描，非法 UTF-8 也提前知道 | 每块追加增加解码 CPU 和状态，收益可能只是从结尾移到实时阶段；首版不采用 |

不默认引入进程池：大对象 IPC、复制、进程生命周期和租户上下文成本尚无证据优于现有线程。也不把所有平台/失败路径一次性改成新的存储协议。

## 4. 阶段 A：拆分测量与复用边界

先在专项 benchmark 中分开记录 pipe 收集、最终边界扫描、解码/编码、artifact 写入、fsync/rename、展示生成、关闭阶段；统计原始/最终字节、读取遍数、fallback 次数及输出 worker 等待。生产指标保持有限类别，不带输出文本、文件路径或租户标签，避免高基数。

在两个 reader 与真实 append worker 完成后，为 stdout/stderr 各计算一次不可变 `(start, end)`，在本次 finalization 内复用。显式传给判空与解码/写出过程，不做跨请求全局缓存。此时文件不可再追加，避免缓存边界过期；stderr timeout suffix 仍独立追加。

小输出内存路径、换行裁剪规则 `strip("\n")`、stdout/stderr 分区和 diagnostic 文案不变。artifact 很小而返回内存字符串的现有分支也保留。

验收：同一次最终处理每流最多一次完整边界定位；全换行只扫描一次该输入，内容结果与现有 smart_decode/formatter 一致。

## 5. 阶段 B：正常 UTF-8 单遍生成

只在阶段 A 数据确认双遍读取有显著成本后实施。

最终 `.tmp` artifact 对外尚不可见。写入某个流之前保存该段起始文件位置，以严格增量 UTF-8 解码器分块读取和编码写出；如果完整解码成功，直接保留该段，不再预校验。每块仍受 64 KiB 输入约束，不能 join 整个流。

如果任意位置（包括 final=True 的残缺尾字节）出现 UnicodeDecodeError：

1. seek/truncate 回该流段的起始位置；stdout 已完成段、失败前缀和 stderr 分隔符的位置必须定义清楚，不能截断其他流。
2. 丢弃当前段尚未返回的 stderr marker 状态，重新建立扫描器。
3. 使用现有 locale preferred encoding 与 errors=replace，从同一原始边界重新读取整个流并写出。UTF-8 前缀不能与 locale 后缀混合。
4. 后续 suffix、diagnostic、flush、fsync、rename、展示引用沿用原流程。

仅捕获编码错误触发重写；磁盘短写、seek/truncate 失败、路径替换等按更新后的严格策略报告存储错误，不得被当作编码问题吞掉。任何 worker 未真正结束前都不能取消文件所有权或关闭原始 spool。

正常 UTF-8 的最终内容读取目标从 2N 降为 N；原始 spool 的一次写入和 artifact 的一次写入仍然存在。非法 UTF-8 接近末尾时可能多写一次大部分内容，这正是方案的主要代价：必须单独压测，不能只展示正常 UTF-8 的最好结果。

## 6. 完整输出回退的边界

保留完整字符串返回语义时，长度为 N 的结果本身就需要 O(N) 内存；全部可用磁盘失败时，也无法同时保证任意长度完整输出和固定内存上限。本轮不能静默截断、丢弃输出或把新的不可访问路径当作有效 artifact。

历史首轮保留 `_full_response` 的兼容行为（已由严格失败策略取代），增加 fallback 次数/字节与峰值测量，减少可以证实的临时副本，但不宣称回退内存有界。

后续独立阶段：Windows 在确实存在合适异步 pipe reader 的运行环境中，可让“已启用压缩”的调用复用 spool，保持终止进程树、超时排空与增量输出语义；必须有 Windows 真机/CI 验证。未启用压缩的同步 API 继续返回完整字符串，不默认强制生成截断引用。

用户随后确认采用“存储失败后终止命令并明确报错”，具体初始化、执行中、最终保存和取消规则见上方严格策略实施记录。该决定改变失败语义，正常输出协议不变。

## 7. 验证与准入

文件范围：`shell_output_spool.py` 为主；只有阶段指标或调用参数需要时才触及 `shell.py`。回归放在 `tests/unit/agents/tools/test_shell_output_spool.py`，延续原超时、重复取消、目录替换、短写、完整 artifact 与失败分类用例。

内容矩阵：0/小输出/8/64/256 MiB；stdout、stderr、双流；纯 ASCII、多字节字符跨 64 KiB 边界、非法 UTF-8 首部/中部/尾部、不完整尾字节、locale 回退；长换行前后缀与全换行；成功、非零退出、超时、取消；fsync/rename/重写 truncate 失败。artifact 内容应逐字节比对旧 formatter 的预期，小输出展示、错误类别和截断引用不变。

用固定时长、多轮交替运行的并发负载测量：最终阶段耗时、读写字节、CPU、output worker 排队、loop p95/p99、RSS 及容器内存；不能再用少于 100 个样本的短窗口证明 p99 改善。阶段 B 准入需同时满足正常 UTF-8 输入读取减少约一半、对应负载最终处理时间改善、正确性完全通过；若非法编码负载稳定恶化超过 20%，先保留阶段 A，重新比较预校验方案。fsync 行为不变，不设未经目标存储验证的绝对毫秒承诺。

## 8. 影响与交付顺序

GitNexus 对 ShellOutputSpool upstream 为 LOW，2 个直接关联、18 个累计符号；_StreamBuffer 亦为 LOW。调用链集中在 Shell 执行与最终响应，ContextVar 注入、取消清理和路径边界仍需要源码测试覆盖。实施前对实际编辑的方法重新 impact。

建议顺序：先阶段 A 的测量和重复扫描消除，再判断是否实施阶段 B；Windows/失败语义作为独立任务，不混入最终解码优化。阶段 A/B 均不移除同步 API，不改截断和持久化协议，不涉及 S3 恢复计划复用。
