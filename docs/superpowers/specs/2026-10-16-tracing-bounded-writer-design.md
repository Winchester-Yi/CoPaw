# Tracing confirmed writes and bounded writer

The approved scope is to repair completion/shutdown first, then implement a single bounded writer using the existing aiomysql adapter. Payload retention and sanitization remain unchanged. No driver or schema migration is included.

`SpanWriter` owns queued and in-flight entries, their accepted and acknowledged versions, retries, and capacity. The manager retains access to pending Span objects for attribution and updates. Each write uses a field snapshot; a concurrent update creates a later version. A barrier captures accepted versions for a trace, including in-flight writes, and completes only after those versions are acknowledged. INSERT and UPDATE failures retain ownership. Trace completion errors propagate without marking the trace completed or removing its active state.

Emission only admits and signals work. Capacity includes in-flight entries; row count and conservative SQL-text byte estimates are bounded. Defaults: 100 rows/256 KiB per batch, 10,000 spans/8 MiB outstanding, 30 seconds for completion and shutdown waits. A single oversized span is admitted only when otherwise empty and written alone, preserving existing payloads without deadlock or silent truncation. This is an explicit exception to the byte budget, not a hard RSS limit; one bounded batch snapshot also consumes memory. Full queues apply cancellable backpressure. Updates reserve their replacement size before acceptance.

The writer starts with a clean Context so it cannot inherit a request transaction/tenant. Source identity is stored on every Span. Failed batches retry with capped backoff. Span INSERT uses idempotent mutable-field upsert under a transaction so driver-generated SQL chunks commit together. Successful processing count, rather than MySQL affected-row count, is returned; duplicate no-op writes can affect zero rows. Stable span IDs and serial version ordering prevent older local retries from replacing later local updates.

Close stops admission, wakes the writer and waits for queued/in-flight/retry work. The manager shields its shared close task from caller cancellation. At the explicit deadline the writer is cancelled and gets a bounded cancellation grace of `min(shutdown_timeout, 1 second)`. `asyncio.wait` bounds this wait without waiting for cancellation acknowledgement. Shutdown raises with unconfirmed counts and reports whether the writer is still running. Cancellation restores in-flight batch ownership when it propagates. If cancellation cleanup stalls, the manager defers storage closure to a background task that waits for actual writer exit and logs late cleanup failures. This avoids pool closure blocking the timeout path. Cooperative cancellation cannot force a stuck coroutine to exit; its resources remain held until it exits or the process terminates. An abruptly killed Pod can still lose memory-only data; no durable spool is added.

Cancellation attempts transaction rollback before returning the connection. If aiomysql has already closed the cancelled connection, rollback errors are logged while the original cancellation is preserved, preventing the writer from retrying past the shutdown deadline.

The budgets do not cover producer-owned inputs waiting for admission or exact Python object overhead. Admission estimation/deep copy, JSON serialization and aiomysql escaping still run on the event loop. Chunking bounds ordinary batch work, not total CPU or the cost of one oversized row. No production latency or throughput improvement is claimed without measurement.

Tests use Event-gated stores to check in-flight barriers, updates during INSERT, retry ownership, caller cancellation, close draining/timeouts, capacity and row/byte chunks. Store tests check transaction and upsert contracts; the existing tracing suite, adapter tests and affected runner/SDK tests provide regression coverage.
