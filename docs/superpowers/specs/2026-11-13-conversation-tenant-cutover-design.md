# 会话迁移按租户隔离失败与独立上线

状态：设计稿，尚未实现。2026-11-13 用户确认：正常租户须独立上线，失败租户保持不可用，修复后补迁。本文不是当前 CLI 操作手册，下面的新参数、状态和表均为待实现契约。

## 1. 边界与不变量

迁移与上线的最小单位是 `(service_unit_id, tenant_id)`。同一服务、同一账号下的所有 source、Agent、workspace 及旧分享共同组成一个单位，不能只上线其中成功的 Agent。不同服务即使账号字符串相同，也不共享发布权限。

正常租户通过完整校验后即可发布并使用 MySQL；失败租户继续维护，不回退到 legacy，也不允许借空 workspace 自动初始化绕过。所有旧版写入者仍须在源冻结前退出。部分上线不引入新旧版本同时写入、双写或增量追赶。

部分上线要求冻结输入与在线可变目录物理隔离，或有能够证明等价隔离的存储冻结机制。`source_root`、配置证据和旧分享正文不能因已上线租户新建 Agent、bootstrap 或修改配置而变化。当前全量手册允许的“直接读原目录”不能直接推定适用于部分上线；若在线运行会改同一 config.json 或受检查的共享父目录，就必须先建立独立冻结快照。不能通过忽略共享证据变化来解决。

以下不变量必须同时满足：

1. 单个租户失败不取消其他租户的工作；同租户失败不能留下可访问的半迁移数据。
2. 租户必须在 workspace、Session、ledger、archive、分享、源复查、数据库映射及运行时根全部通过后发布。
3. 发布是数据库中的原子状态变更。日志、JSON 报告、缓存及进度计数不授予访问权限。
4. 已发布租户不可再由迁移程序修改、重新解析或按旧源校验。运行时新增、删除及分享计数不得被补迁覆盖。
5. 未确定归属的数据必须保留，不能通过删除 blocker 或缩小清单伪装全量成功。
6. 作业仅在冻结清单的全部租户和未归属项全部完成时为 `ready`。`partial_success` 只表示已有租户发布。

## 2. 当前实现与改动落点

| 当前行为 | 改动要求 |
| --- | --- |
| `discovery.py::discover_services()` 有 blocker 就跳过全部语义盘点 | 按可信租户分组盘点，记录失败后继续其他组 |
| `_profiles()` 在配置级捕获错误，可能已经加入同租户部分 workspace | 先收集候选及租户关联，再决定整个租户是否完整；不能使用半组作为成功范围 |
| `inventory_parallel.py::spool_workspaces()` 的预检异常使协调器退出 | 捕获明确的租户数据错误，封存该组失败；共享故障仍终止 |
| `conversation_storage_v3_cmd.py::_execute_spooled()` 要求全 inventory ready | 各租户独立预检、导入、校验、发布；共享 schema 校验独立执行 |
| `journal.py` 只允许一个 job 且扫描全库业务行 | 保留单 job，新增租户状态；所有权检查只验证未发布租户及其迁移票据 |
| `compare_original_shares()` 比较全表全部旧字段 | 补迁只比较本次未发布租户的冻结旧行；已发布租户可新增分享及更新计数 |
| finalize 要求完整作业 ready 并输出完整凭证 | 增加租户发布事务和部分运行时凭证；旧全量流程保持原契约 |
| `runtime.py::for_workspace()` 可接纳未映射空目录 | 部分模式先检查租户准入，不能通过空目录加入 |
| 分享不经过 workspace 门禁 | 分享读写、访问计数和 pin 前也检查发布状态 |
| `backup_authority()` 只查 ready jobs | 备份和恢复支持已发布租户凭证，不把未发布租户当空数据 |

## 3. 发现与失败归属

发现分为服务校验、配置/身份收集、覆盖核对、租户语义盘点四步。每步都尽量收集完整错误，不因首个可隔离的数据问题退出。固定会话输入枚举范围、容量门禁、软链接与特殊文件拒绝规则保持有效。

先建立可信租户目录，包括无 Agent 的账号、空 workspace 和仅剩分享的账号。账号身份从现有配置布局、可信配置字段或审核 override 取得，不能从异常文本猜测。失败账号的全部候选仍登记在冻结覆盖证据中。

错误分为：

| 影响范围 | 例子 | 行为 |
| --- | --- | --- |
| 租户 | 配置字段异常、会话超限、ledger 损坏、一个 Agent 失败、该租户分享缺正文 | 隔离整个租户，继续其他租户 |
| 服务 | 服务根无效、同服务 workspace 归属冲突、未知目录无法归属到可信账号 | 继续收集其他服务的发现结果；受影响服务不得发布 |
| 多租户 | 同一分享存在多个服务候选且账号可信 | 冻结候选归属证据，阻断所有候选租户，不能任选一个 |
| 作业 | schema 不符、数据库不可用/提交结果未知、锁丢失、临时盘满、共享 NAS 根不可用、程序错误 | 停止接收新工作，排空 IO，保留断点后失败退出 |

单个缺失文件属于租户错误；无法证明影响范围的 EIO、断链、权限或容量错误不得一律转换为“跳过账号”。只捕获定义清楚的领域异常；`CancelledError`、未知异常、`UnknownCommit` 不被吞掉。

未归属项单独记录，不伪造账号。若可以证明它仅影响某个服务，则只阻断该服务发布；不能证明与正常租户无关时，宁可扩大阻断范围，也不能泄漏或漏迁。正常租户可以继续解析和导入，但受影响范围在证据消歧前不能发布。

## 4. 持久化状态与重试

保留一个 migration job，新增 DBA 预建的 `swe_conversation_migration_tenants`，唯一键为 `(migration_id, service_unit_key, tenant_key)`。不得用临时 JSON 的成功布尔值代替 SQL 状态。

租户行至少包含：阶段状态、失败阶段、错误码、脱敏原因、失败次数、范围证据版本、已校验摘要、发布版本与时间、更新时间。详细字段类型、索引和迁移 SQL须随实现补充并纳入 `check_schema()`。

状态流转：

```text
discovered → importing → imported → verified → published
     ↓           ↓          ↓          ↓
   failed ← 租户级失败；修复后通过显式 retry 回到相应未完成阶段
```

`published` 是终态，重试不能回退。租户失败不回滚其他已提交租户，也不大批删除失败租户已提交票据。重试仍使用同一 migration_id、稳定源键和 SQL journal，逐项确认已有提交后继续；不得把未知提交当作普通失败跳过。

如果修复改变冻结内容，必须登记该未发布租户的新证据版本，清楚区分：

- 配置/可信映射修正且现有票据语义不变：复查后续跑。
- 源内容或已提交实体语义改变：禁止直接重绑原票据；需显式、可审计的租户重置/重建流程，先证明未发布且无运行时写入，并完整处理依赖。初版不支持自动重置，给出明确阻断原因。

重复进程仍由现有 schema 级迁移命名锁排斥；不得为提高并行度启动多个迁移进程。一个进程保留单 SQL owner、有界 IO 并发。租户失败后先结束/排空该租户已提交任务，再将状态记为 failed；不得先发布再等待线程结束。

## 5. 发布事务及覆盖证明

每个租户发布前：

1. 本租户冻结的全部 workspace、Agent、Session、archive、ledger 与分享均已导入。
2. 全部 journal/SQL/正文语义验证通过，数量与集合覆盖一致，没有未映射数据。
3. 本租户源会话输入及明确配置证据复查通过，原分享行在未发布期间未变化。
4. runtime workspace 根、NAS 根、服务和数据库身份一致；无受影响的服务级未归属 blocker。
5. SQL 事务锁定租户状态，复核证据版本和完整校验摘要，然后原子写入 `published` 与发布证明。

租户发布与文件凭证输出之间崩溃时，以 SQL 为准，重跑只补输出，不重导入。发布前崩溃不得被 runtime 当成已发布。manifest/SQL 证据不一致、CAS 冲突或缺少完成批次均拒绝发布。

已发布 A 租户在线新增业务行时，补迁 B 仅检查 B 的范围所有权及 B 的票据。不能删除原有全局未知行保护后放任未知 B 行；也不能要求 A 的运行时新行都拥有迁移票据。存在范围冲突、跨租户关联或外来未发布行时仍阻断。

## 6. 运行时准入与多实例

增加显式部分迁移运行时模式及版本化凭证；旧 v1 authority receipt 和旧全量 ready 流程不被隐式重新解释。部分模式启动须校验数据库、服务、NAS 和 job 身份，但不要求所有租户已发布。

初版优先采用数据库直接检查发布状态，不使用会长期保留失败结果的进程缓存。若后续缓存，必须有明确失效/刷新协议；“改完文件等重启”不是独立上线方案。

准入检查覆盖：

- 租户 bootstrap、workspace 装配或任何会改写旧目录的初始化之前。
- HTTP/Channel/runner 新请求、历史读写、恢复、定时任务、后台 worker 和外部命令入口。
- 已缓存 workspace 的每次新业务操作，不能只在首次创建 adapter 时验证。
- 分享创建、列表、详情、匿名读取以及访问计数；匿名读取在加载可信归属后、读取正文/pin/更新计数前检查。
- 备份、恢复、导出及可能处理未发布数据的 GC/retention 流程。

失败/未发布账号返回统一维护中错误（HTTP 503，带稳定机器码），不输出内部路径、SQL 或失败内容。匿名分享不泄漏账号和原因；不得因拒绝访问增加计数。数据库不可达时准入失败关闭，不回退 legacy。

初版部分模式对未登记新账号默认拒绝；新账号启用须走独立的可信空账号登记流程，不能靠请求指定一个新 tenant_id 绕过门禁。发布后的租户可创建正常的新 Agent/workspace，但仍遵守原身份和非空旧目录检查。

## 7. 分享表与补迁期间的 DDL

当前分享表 `service_unit_key` 全表 NOT NULL 收紧是全量门禁，存在失败租户旧行时不能完成。部分模式必须允许受控的 nullable 过渡结构；所有已发布租户的分享行必须具备正确 service key 和完整 locator，应用写入的新分享始终完整。

不能为了收紧 DDL 删除失败租户分享、填默认 service 或虚构 publication。未映射旧分享必须保持不可访问；服务匹配失败也不能回退旧文件读取。

部分模式的 schema 验证须明确区分“获准的过渡结构”和“结构不符”，不可普遍放宽运行时 schema 校验。全量收尾时复查所有旧行均完成，再按 DBA 手册执行 NOT NULL 收紧及最终 schema 校验。补迁不改已发布租户的 share counters、last_access_at 或新增分享。

过渡结构与最终结构须有明确的发布版本/能力契约，启动程序不能仅凭列允许 NULL 就默认支持部分迁移。最终 DDL 需安排 DBA 执行窗口，评估 metadata lock 与在线请求影响，失败时保持过渡模式；不能在任意活跃请求期间自动执行 DDL，也不能先更新完成状态再实际收紧。

## 7.1 GC、备份恢复与回滚

未发布租户已有的 prepared、committed 正文和 legacy source 引用，需要持久迁移保护或可恢复租约覆盖；作业退出、故障或超过普通 pending 清理时间也不能被全库 GC 当作孤儿删除。租户准入门禁本身不能代替 GC 保护。发布事务衔接正常引用保护，失败租户的保护只在明确完成或审核放弃/清理后释放。

部分备份只接受已发布租户的完整集合，证明中记录准确的租户范围和发布版本；恢复不能自动把备份未包含的失败租户提升为已发布。全库备份/恢复必须额外保存迁移状态与保护关系，不能只复制业务行丢失断点。部分迁移期间不允许对在线租户运行会覆盖其新写入的整库回滚。

已经上线的租户如需回滚，必须按其完整新提交状态导出，并核对跨租户依赖与分享；共享旧镜像不能在其余租户仍使用新版本时重新取得写权限。无法证明租户隔离回滚安全时，扩大维护范围后进行一致的全量回滚，仍不得恢复旧快照丢弃上线后的提交。

整体灾难回滚须有独立的受控管理路径：先停止并排空全部新旧写入，再以已发布租户的最新完整 SQL/NAS 状态、未发布租户的冻结旧输入分别作为权威，合成为固定旧版本可读的完整输出。未发布租户的半成品 SQL 不能当成完整数据；job 未 ready 也不能使安全管理导出无路可走。原分享表已含上线后的更新，合成时按租户选择权威，不能用原始全表覆盖已发布租户计数。该路径须单独验证，不能沿用普通业务准入绕过授权。

## 8. CLI 与报告契约（待实现）

采用显式模式参数，旧命令默认保持严格全量行为。例如拟新增 `--tenant-isolation`，该选择写入 discovery/manifest，后续阶段继承，不能在 resume 时临时打开以绕过旧 blocker。旧 manifest 不自动转换，需专门校验的升级流程。

部分模式各阶段输出 `status`、成功/失败/待处理/已发布租户数，以及失败清单文件位置。建议退出码：0 全量阶段成功，2 存在租户失败但正常租户已处理完，1 共享故障，130 人工中断。Shell 处理 2 必须检查 `status=partial_success`；不能用 `|| true` 忽略任何失败。退出码 2 不是全部上线成功。

面向运维的失败清单只列：

```json
{
  "service_unit_id": "SERVICE_A",
  "tenant_id": "account-a",
  "stage": "inventory",
  "code": "session_invalid",
  "reason": "会话数据不完整"
}
```

同一账号多项错误可聚合原因，按服务+账号去重。正文、凭据、原始 SQL、分享 token 和内部路径不进入该清单。受保护的详细诊断保留定位键、完整性证据和重试记录。无法识别账号的记录列入独立未归属清单，不冒充失败账号。

`discover` 继续全范围扫描并生成成功/失败分区；`freeze` 固定完整覆盖和失败集合；`import/resume` 仅处理未发布、已具备可信范围的租户；`verify/finalize` 对租户完整校验并发布；`retry --failed-tenants`（拟定）只选失败且未发布者。独立上线按每个租户发布结果开放，不必等待整批命令返回。全量完成后才输出最终完成凭证。

## 9. 验收与交付顺序

必须由独立子代理核对代码及文档；实现前后均不宣称旧手册已支持部分上线。拆分实现但在整个闭环通过前不公开开启部分模式：

1. 范围/错误归属、SQL 租户状态与版本化证据。
2. discover/freeze 的隔离与完整覆盖；有界任务失败局部排空。
3. 导入/续跑/验证/发布，以及限定租户的所有权和分享比较。
4. 启动、业务请求、后台任务、分享、备份恢复与 GC 准入。
5. CLI 退出码、失败清单、补迁操作手册和兼容性。

关键验收矩阵：

| 场景 | 必须结果 |
| --- | --- |
| A 正常，B 配置/会话失败 | A 完整发布可用，B 所有入口维护中，整体 partial_success |
| B 仅一个 Agent、ledger 或分享失败 | B 全部 source/Agent 不发布；A 不受影响 |
| A 在线新增消息、删除、产生新分享并更新计数，随后补迁 B | B 成功；A 不被重新读取旧源或改写，运行时变化完整保留 |
| B 部分提交后断链，提交结果未知 | 立即停止该轮；原作业恢复后核对票据，无重复和假成功 |
| 发布前崩溃、发布事务后文件输出前崩溃 | 前者不可访问；后者可由 SQL 证明恢复凭证，不重导入 |
| 两实例，B 初次请求被拒绝，之后发布 | 两实例无需整体重启即可接纳 B，失败状态不被永久缓存 |
| B 空 workspace、bootstrap、缓存 adapter、cron、匿名分享 | 发布前均无法绕过，不读正文、不写数据、不加分享计数 |
| 服务归属歧义、未知 workspace、重复 scope/root | 完整保留证据并阻断受影响范围发布，其他可证明独立的范围继续 |
| share-only、空账号、同名跨服务账号 | 范围完整且互相隔离，不因没有 workspace 漏迁 |
| 无关附件、深目录与真正会话超限 | 保持现有包含范围与容量限制；只影响可归属租户 |
| 锁丢失、盘满、数据库故障、取消 | 不吞异常、不继续发布、排空真实 IO，断点可复核 |
| 备份恢复和 GC 与补迁并行 | 不采集半迁移租户，不删除待迁移旧数据或跨租户依赖 |
| A 在线新建 Agent/修改配置，B 仍未发布 | 独立冻结证据不变；不具备隔离条件的布局拒绝部分模式 |
| 最终 DDL 遇到 metadata lock 或失败 | 不错误宣称收紧完成，过渡模式保持可用，窗口内可重试 |
| A 有新消息和访问计数，B 半迁移，停止写入后整体回滚 | 合成 A 最新完整状态与 B 冻结输入；不漏数据、不导出 B 半成品 |
| 旧全量 manifest/receipt/CLI | 原拒绝规则与成功契约保持有效 |

验证仅使用本地临时目录和授权的隔离 MySQL 测试 schema；不运行万级基线、不读取业务 schema、不做服务端监控或额外压力实验。真实 NAS 性能与生产上线仍需另行验收。
