# SSE 日志批量读写方案

状态：连续读取、有界 writer 与 TaskTracker drain 已实现。设计基线为 `159cfb292`；本轮回归及性能对比基线为 `d2963d586`，分支 `perf/event-loop-optimization`。

实现验证：覆盖连续读取、批次回滚、大帧、全局预算、取消前后提交、重复取消、空错误文案、关闭尾批次和重连水位。性能数据另见 [本地测量](../benchmarks/2026-10-15-sse-batching.md)。本地结果不能替代 Linux/Kubernetes 固定时长多轮、32 租户、容器内存和目标存储验证；后者保留为上线前验证。

当前默认：按用户决定，TaskTracker 默认启用 offer 聚合；`SWE_SSE_BATCH_WRITES=0` 可按轮切回等待提交的 append。连续读取默认生效。已有本地测量显示突发任务数减少约96%，同时稀疏交付中位数增加5–6ms、16租户交付p99上升；默认开启不代表 Linux/Kubernetes 准入测量已完成。

## 1. 结论与约束

推荐分两步实施：先优化连续读取，再增加有界入缓冲与批量追加。保留现有 `append()` 等待提交完成的兼容入口，TaskTracker 单独接入允许短时聚合的新内部入口。没有后续事件可进入缓冲时，单纯在现有 append 内等待定时器不能实现同一生产者的批量化。

不改变 SSE frame、turn-bound ID、客户端应用后推进 cursor、去重/缺口检查、终态 snapshot、原有日志配额和单帧上限。临时日志仍无每事件 fsync，也不增加跨进程/Pod 恢复。所有完整业务事件保留，不能通过合并 JSON delta 或丢弃事件降低任务数。

## 2. 当前成本与证据边界

- `TaskTracker._producer` 每生成一条事件，就等待 `_broadcast_sse`，后者等待 `ReplayStream.append` 完成磁盘写入。
- `ReplayLog._append` 每条事件单独编码、seek、write；`ReplayStream` 每次提交后唤醒订阅。
- `_read` 已支持每次最多 64 条/64 KiB，但当前对每个 record 分别 seek、读头、读内容。及时消费的实时订阅常常只能看到一个已提交事件，无法用满批次。
- 现有模拟把 `append(event)` 和 `fast.get()` 串在同一个协程中。2 万条事件的 4 万次 worker 任务证明逐事件调度成本，但这种串行握手本身限制批量化。它不代表真实 HTTP 吞吐下降 25 倍，也不能作为新批量实现唯一验收负载。

## 3. 方案比较

| 方案 | 收益 | 限制 |
|---|---|---|
| 只做连续读取 | 降低历史追赶的 seek/read 次数，保留全部调用语义，改动小 | 不能减少串行生产者的写 worker 次数 |
| 有界入缓冲、批量写入、连续读取（推荐） | 同时减少 worker 提交、磁盘小写及实时读取任务 | 增加 pending/committed 两阶段和显式 drain 生命周期 |
| 增加共享近期 payload 缓存 | 可减少稀疏实时读取的磁盘任务 | 额外缓存预算、淘汰与引用生命周期；首版暂不引入 |

## 4. 新的内部接口与状态

以下为拟新增内部接口，不是对外 API 承诺：

- `offer(event) -> sequence | None`：等待有界容量，原子地加入待写缓冲并分配序号，然后返回；返回不代表已经提交。流已结束或传输错误时沿用当前传输停止行为，不能因此取消业务 Agent。
- `flush(through_sequence)`：主动唤醒 writer，等待指定水位真正写入完成或传输失败；用条件通知等待水位，不为每个事件常驻一个 Future。
- `append(event)`：兼容包装，offer 后 flush 并等待该事件提交；原调用方和测试的完成语义保留。
- `end()`：禁止新入缓冲，排空所有已接受事件，设置 ended 并唤醒订阅。只有 drain 完成才能出现正常 EOF/stream.end。

序号满足 `committed <= accepted`。只有完整写入成功的连续前缀才推进 committed；pending 事件不进入订阅可见区，也不能被 resume 当作有效的未来游标。

每轮一个 writer 协程，只有出现待写数据才等待定时器或容量条件，不做空闲轮询。每轮最多一个正在执行的 append worker；全局继续复用独立 2 线程/4 个提交许可。容量预留、序号分配和入队在 loop 上无 await 地完成；不再需要 publisher 锁，容量等待不持锁。

## 5. 聚合、容量与背压

初始参数是待压测验证的起点，不是性能承诺：

| 项目 | 初始设计 |
|---|---|
| 一批事件条数 | 最多 32 条 |
| 聚合触发目标 | 约 64 KiB 输入，或达到条数阈值 |
| 最长主动聚合等待 | 首条入缓冲起 5 ms；新事件不能不断重置 deadline |
| 每轮未提交条数 | pending 与 in-flight 合计最多 64 条 |
| 每轮普通未提交对象内存 | 256 KiB，包含仍由 writer 引用的输入对象与记录开销 |
| 大帧兼容 | 超过普通缓冲预算的单帧独占该轮未提交区；仍受 1 MiB UTF-8 帧限制，原 Python 字符串可能因 Unicode 存储占用约 4 MiB |
| 进程未提交对象总预算 | 32 MiB，大帧也必须预留；不新增无限等待队列中的 payload 副本 |
| 读取 | 沿用最多 64 条/64 KiB，单个大帧例外 |

入缓冲按字符串实际对象大小与记录开销计量，不能只用字符数量代替内存。编码、精确 UTF-8 帧大小检查和记录拼装在 worker 执行。64 KiB 是聚合目标；编码后较大的批次拆成有界连续写块，合法单大帧单独处理。worker 不拼接整轮内容，单 worker 编码/拼装临时空间设计上界 8 MiB，独立 2 worker 的临时空间另计最多 16 MiB；实施时用分配峰值验证，不能把 32 MiB pending 预算当成总 RSS 上限。

达到容量后等待 writer 释放容量，形成对生产者的背压。等待期间不持有 TaskTracker 全局锁或磁盘锁。内存许可在 worker 真正结束、输入引用释放或失败清空后释放。每个调用方最多持有自己尚未接受的一条事件，不能后台创建每事件 task 绕过条数限制；实际并发调用方的栈引用另受请求并发约束。

5 ms 只限制主动聚合时间；worker 排队和磁盘延迟可能更长，必须分别计量。短输出在 end/flush 时立即提交，不等 deadline。客户端断开不触发整轮 flush 或取消 producer。

## 6. 文件写入与连续读取

`append_many` 在 worker 内锁定本轮日志，先验证事件大小、条数和总日志容量，再预留整批日志/索引配额。记录仍采用原长度头加 UTF-8 格式。

成功时写完批次全部字节后安装 offsets、更新 count，返回提交水位；loop 再推进 committed 并一次性通知订阅。短写或异常时截断回批次起点、回滚新索引和预留，不能公布部分批次；截断失败则保留实际可能占用的配额直到关闭。先前已提交批次不受影响。编码失败或配额失败沿用明确的传输不可用控制，后台业务继续。

`_read` 根据 offsets 与批次可见水位计算连续文件区间，执行一次 seek 和有界 read，在 worker 内解析每条长度头、UTF-8 与序号。仍校验短读、非法长度和游标，不能把尚未 committed 的新记录提前暴露。物理批次不会改变逻辑事件的 ID 或客户端 reducer 调用次数。

首版不为凑读批次额外延迟订阅，不引入近期缓存。写入一次公布多个事件后，实时订阅自然能够读取多条；历史追赶也会减少系统调用。

## 7. 取消、失败与结束

- 入缓冲前取消：不分配序号、不占用容量；预留与入队之间不留可取消 await。
- 入缓冲后 producer 取消：`finally` 进入独立 drain，等待已接受批次完成再传播取消；重复取消和 AnyIO disconnect 清理继续使用已有保护。
- worker 取消等待：线程真正完成前不关闭文件、不释放执行许可。writer 不能把协程取消视为写入未发生。
- 正常结束/业务异常：先 flush 再结束传输；业务异常帧必须在对应 flush 边界内。
- TaskTracker 生命周期：现在 producer finally 先从 `_runs` 删除再 end。改造后要保证末批 drain 期间仍有可发现的运行传输，drain/错误收敛后再移除，避免重连越过尚未公布的尾部。
- `close()` 与追加竞争：先原子进入 closing、固定最后 accepted 水位，再 drain；之后不能接受新事件。TTL 只关闭已结束日志，不能关闭正在使用的 worker 文件。
- 磁盘失败：停止后续传输写入、释放 pending 引用、唤醒 writer/容量等待者/订阅，输出不可用控制；不能永远等待 flush。

## 8. 验证与分阶段交付

第一阶段修改 `sse_replay.py` 的连续读取，并增加读系统调用计数测试；不改变发布语义。第二阶段加入 writer、offer/flush 和 TaskTracker drain，保留兼容 append。相关回归集中在 `test_sse_replay.py`、`test_task_tracker.py`、Console ASGI/续传测试。

必须覆盖：32 条/字节阈值/5 ms deadline、单事件立即 end、稀疏输出、大帧与多字节 Unicode、并发 emitter 的顺序、历史追赶接实时、批次任意位置短写、截断失败、配额拒绝、容量等待取消、已接受事件取消、重复取消、关闭竞争及锁竞争 ASGI 断连。资源关闭后所有 pending/日志/订阅预算归零。

改写 benchmark 为独立 producer/consumer 协程；保留原串行握手作为低并发兼容场景，不用它推导批量上限。测试稀疏 20 event/s、突发 2000 event/s、4/16/32 租户，一快一慢及历史重连。固定运行时长并多轮交替采样，记录 worker 任务数、每批条数/字节、触发原因、入缓冲等待、accepted-to-committed、落盘到客户端应用、loop p95/p99、RSS、容器内存与临时目录。

初始验收目标：突发小事件场景 worker 提交数相对当前版至少减少 75%，端到端完成时间改善；稀疏场景不超过配置的主动聚合等待，额外调度/磁盘等待单独报告；所有正确性和容量约束必须通过。Linux 同负载多轮 p99、RSS 或容器内存出现稳定恶化时不默认开启新 writer，保留旧同步提交路径回退。指标不达标就调整或停止该阶段，不预先承诺恢复到纯内存模拟耗时。
