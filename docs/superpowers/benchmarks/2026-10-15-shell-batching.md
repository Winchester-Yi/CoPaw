# Shell 批量写入测量

在同一份新实现中仅替换 `shell._SHELL_SPOOL_BATCH_BYTES`，依次比较 4/64 KiB，再交替比较 16/32 KiB，各运行三次独立 Python 进程。使用现有 `benchmark_event_loop_followups.py` 默认负载：4 个租户、每个 16 MiB stdout、4096 字节展示、10000 条 checkpoint events、mock S3/Provider。4 KiB 模式复现逐块提交数量，并非完整旧版本。平台 Darwin，没有真实 HTTP/模型/数据库/S3。

| batch | output 完成任务 | 总耗时范围 (s) | loop p95 范围 (ms) | loop p99 范围 (ms) | RSS 采样峰值范围 (MiB) |
| --- | ---: | ---: | ---: | ---: | ---: |

| 16 KiB | 4108 | 0.671–0.681 | 1.116–1.140 | 23.454–25.765 | 186.16–186.83 |
| 32 KiB | 2060 | 0.510–0.583 | 1.118–1.161 | 4.706–26.983 | 187.11–187.75 |
| 64 KiB | 1036 | 0.465–0.526 | 1.079–1.145 | 8.428–26.038 | 187.84–189.67 |

保留 64 KiB：该负载任务数量降低约 93.7%，耗时下降，RSS 接近。较小批次没有稳定消除 p99 尖峰，因此不能把 16/32 KiB 宣称为延迟更优。批量写入的短窗口样本不足 100 个，p99 接近最差采样；4 KiB 模式窗口更长，样本数量不同。最终 artifact 工作等阶段仍会与 loop 竞争 GIL，本次数据不能定位尖峰来源，也不证明生产 p99 无回归。需要固定时长/重复请求的 Linux 负载进一步验证延迟分布。
