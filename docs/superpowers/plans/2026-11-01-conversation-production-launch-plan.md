## 2026-11-02 补充：如果上线后不退回旧版

以下是可选上线策略：切到新版后，故障通过修复新版或恢复到同一套 MySQL/NAS 存储的
可用状态处理。选择这条路线时，本文后续“退回旧版”的要求不再作为上线门槛；
保留原文供另一条路线参考，不表示本次已经执行切换。

- 可以取消：旧格式反向导出、固定旧生产镜像验读并继续写、导回旧目录和旧分享索引的演练。
- R3“导出 CLI 依赖原迁移目录”只影响这条旧格式导出路线，可移出此次上线阻断清单，
  登记为未使用能力的已知限制；不等于该问题已经修复。
- 仍须完成：全部历史迁移核对、服务单元隔离、长期会话验证、目标数据库和双节点 NAS
  验证、多实例停止/重连/审批、全部范围的一致性备份和新版恢复演练。
- 故障处理：关闭入口和定时任务，停止并核实所有写入，保存现场；根据实际状态修复新版，
  或将匹配的数据库与 NAS 备份恢复到隔离目标，核对通过后受控恢复服务。结果未知的
  已提交操作先对账，不重新执行外部工具。
- 恢复旧备份前，必须处理备份之后的新增问答和计数；未验证如何保住这些数据时，
  不能直接覆盖在线系统。放弃旧版回退不代表允许丢数据。
- 停机预算改为“正常切换耗时 + 故障诊断、修复或新版恢复余量”。此路线可能需要更长
  停机处理故障，应提前安排能修代码和处理数据库/NAS的当班人员。

原数据和最终迁移备份继续只读保留，清理另行决定。不需要为了这条策略删除现有导出代码。

这条路线的完成标准是：全部范围数据正确、功能正常、新版备份确实能恢复并继续写、
已验证新增数据的保全方式，且观察期指标正常。

## 先把事情说清楚

这次上线把会话的目录、索引、执行状态等交给 MySQL 管，聊天正文继续放在原 NAS。
原业务 workspace 和 NAS 继续使用，不新建一套业务 workspace。

采用一次连续停机切换：关闭入口，停止全部旧版写入，备份，导入，核对，切表，启动新版，
验证后再开放。所有生产租户、来源系统、Agent 的会话一起切换。
不能让一部分旧版和一部分新版同时接收生产会话写入。

现在先完成下面四件事，再定正式上线时间：**修完三个问题、查清全部历史数据、在目标环境
完整演练、证明失败后能保住新数据退回旧版。** 本地测试通过不能替代这四件事。

## 第一阶段：修好代码，把操作工具准备齐

| 要做什么 | 用人话解释 | 做到什么才算完成 |
| --- | --- | --- |
| 修复多范围恢复 | 多个租户、来源系统和 Agent 的备份，要能一起恢复到同一个数据库 | 在一个空目标库恢复全部范围，所有历史、分享和恢复内容核对一致；同一租户的旧分享不重复 |
| 修复长期会话上限 | 聊天和定时任务历史多了以后，不能因为一次处理数量超限而读不了、写不了 | 覆盖 4096、4097 以及更大引用量；新请求、重启后读取、继续写、取消和失败清理都正常 |
| 修复导出对旧路径的依赖 | 已有完整备份时，即使原迁移快照没挂上，也要能导出回旧格式 | 卸载测试用旧快照后，正式导出命令仍能成功；用旧版读回并继续写 |
| 固化备份、恢复和回退工具 | 运维拿到发布包就能照着执行，不依赖某个人电脑里的临时脚本 | 全范围备份/恢复、导出、恢复旧目录及分享索引都有正式脚本和操作说明；默认预览，明确目标，有日志，失败会停止 |

修复后重新做独立审查。对最终发布版本重跑单元测试、真实数据库集成测试、Console 兼容测试
和相关主线回归。必须运行的测试不能因环境没配好而跳过；静态检查中的既有问题单列，
新增问题必须处理。

产物：修复提交、测试结果、正式操作脚本、更新后的操作手册。
上一轮放在 `/private/tmp/` 的复现和演练脚本只能作参考，不能直接作为生产交付。

## 第二阶段：把要迁的数据查清楚

开发、业务数据负责人和运维一起列出全部生产租户、来源系统、Agent、workspace、用户和
会话的对应关系，确认每个目录属于谁，不能靠猜文件名补身份。

现有本地全量扫描已经发现 6 个关联 Session 缺源文件、107 个 Session 文件缺可信身份映射。
这是本地样本的问题记录，不代表生产一定有相同数量；生产也必须完整扫描。

处理规则：

- 缺文件就查原始目录或可用备份；缺映射就从可信配置或业务登记中补齐。
- 找不到的记录要明确交给业务数据负责人处理，保持上线阻断，不能静默丢弃或伪造数据。
- 老分享也要完整登记，包括原聊天已删除但链接仍可访问的分享，以及访问次数。
- 已确认不属于此次业务范围的文件，要写清依据；不能为了让报告通过而排除坏记录。
- 提前扫描用于找问题；上线当天停止全部写入后，还要以最终备份重新扫描和核对。

通过条件：所有生产范围都在清单内，迁移阻断项为零，旧数据与新数据逐项核对通过。
只比较聊天数量不够，还要比较内容、顺序、状态、标题、绑定、归档、分享和恢复信息。

## 第三阶段：在实际要用的环境里演练

使用隔离数据库和隔离测试目录，验证实际目标 MySQL/TDSQL 与生产等价 NAS；不拿业务表
和业务正文做破坏性故障测试。验证用 NAS 应保持与生产相同的存储后端和挂载条件。

| 检查项 | 必须证明的事情 |
| --- | --- |
| 数据库 | 所需表结构、权限、查询和整批切表操作在目标实例能正常执行；被锁住或中途断线时不会误判成功 |
| NAS | 两个运行在不同节点的 Pod 都能看到完整正文；同时发布不会互相覆盖；缺失、截断、写入失败会明确报错 |
| 多实例路由 | 同一会话的停止、重连、审批请求能找到正在处理它的实例；实例消失后不会显示假完成 |
| 进程故障 | 杀掉测试实例后，可以核实它确实退出、写入已结束，再恢复会话状态；不会重跑已执行的外部工具 |
| 完整恢复 | 全部范围恢复到同一个空目标数据库和空恢复目录后，能重新读取并继续写 |
| 退回旧版 | 新版新增问答、压缩历史、停止、删除、改绑定和更新分享计数后，导出给固定旧版镜像，旧版仍能读和继续写 |

这里的“旧版镜像”必须是实际上线前使用的固定版本，不能用当前源码的兼容读取器代替。
外部工具已经做出的业务操作不会因回退而自动撤销，恢复时也不能自动再执行一遍。

再用完整规模的隔离数据副本演练一遍“停写到开放入口”，包括故意失败后的回退。
记录备份、导入、核对、切表、启动、验证和回退分别耗时多少，以及内存、NAS 空间、
文件数量、数据库锁等待和接口延迟。

**停机窗口按实测结果申请：正常流程耗时 + 故障处理余量 + 对应阶段的回退耗时。**
启动新版之后的回退需要搬回新数据，通常涉及更多步骤，要单独测量。
现在不能拿本地小样本的 98 秒演练结果承诺生产时长。

| 数据负责人 | 全部范围清单、历史问题处理结果、迁移核对规则 |
| DBA | 目标数据库核查结果、迁移账号、隔离建表与切表结果、恢复步骤 |
| 运维 | 原 NAS 和 workspace 挂载、网关会话路由、入口/定时任务/自动重试的关闭与恢复方法、Pod 停止方法 |
| 测试与业务验收人 | 测试账号、历史样本、分享链接及逐项验收清单 |
| 上线负责人 | 停机公告、当班人员、每步负责人、继续或中止的判断、回退决策时间 |

另外准备：可用的旧版固定镜像、备份空间、恢复空间、发布配置和日志存放位置。
新配置要明确启用 MySQL 会话权威、使用审核过的 workspace 映射和归档游标密钥。
安装工具依赖的 SQL 文件必须随审核过的源码/运维包交付，不能只带一个缺少脚本的 wheel。

上线负责人在执行前填写以下空项，不在现场临时猜：

- 停机开始时间、预计开放时间、最晚中止时间。
- 未启动新版前，以及启动新版后的两套回退耗时预算。
- 排空等待上限；超过上限如何中止本次上线。
- 测试环境测得的接口延迟、错误率基准及生产暂停放量阈值。
- 上线后的重点观察时长、值班安排、备份频率、保留时长和恢复时限。

上述准备不齐，或三个已知问题仍未修复，就不进入正式停机。

## 上线当天按这个顺序走

每步记录操作者、开始/结束时间、执行版本、结果和日志位置。上一项没通过，下一项不开始。

| 顺序 | 具体动作 | 继续条件 |
| --- | --- | --- |
| 1 | 发出维护提示，关闭网页/API/通道的会话入口、分享访问、定时触发和自动重试 | 确认没有新任务进入；分享访问会改计数，也要停 |
| 2 | 等待正在回答、执行工具、等待审批和收尾的任务处理完 | 没有活动或结果未确认的任务；超时按旧版流程处理并中止本轮，不能直接当完成 |
| 3 | 停止全部旧 Pod、后台任务和维护脚本，关闭可能自动拉起它们的机制 | 核实所有会话 writer 都停止，而不是只摘掉一个服务入口 |
| 4 | 保存最终旧数据备份、分享数据、配置、身份清单和旧版镜像信息，把源备份保留为只读 | 备份可读、清单完整；备份失败就停止 |
| 5 | 根据最终备份生成本次迁移清单，扫描、预览，再导入隔离的暂存库和 NAS 新前缀 | 无阻断项，导入成功；原 workspace 和旧文件保留 |
| 6 | 完整核对全部迁移结果 | 所有范围逐项通过；缺文件、身份不明、内容不一致均不得放行 |
| 7 | 核对目标、权限和锁状态，执行七张会话相关表的整批切换，保存切换记录 | 确认实际表名完整切换，其他业务表未变；状态不明先查清，不盲目重试 |
| 8 | 保持用户入口关闭，只启动一个新版实例 | 确认原 workspace/NAS 和数据库权威配置正确，启动检查通过 |
| 9 | 用专用账号做读写验证，再启动所需的新实例验证多实例场景 | 下方验收项目通过；旧版实例始终不启动 |
| 10 | 逐步开放新版流量，确认正常后恢复定时任务和重试机制 | 指标在约定范围内，定时任务无重复执行，负责人确认继续 |

第 10 步只是逐步恢复流量，所有会话已经整体切到新存储，不是按租户混用两套存储。

受控验证至少包括：老会话列表和正文、长历史和归档、精确问答、创建/重命名/删除、
专家绑定和解绑、新增问答、停止后状态、重连、审批、老分享/孤立分享/访问计数、
新分享、Cron 回执、W+ 相关会话，以及跨用户/租户不能读到别人的数据。
生产受控验证不随意杀掉承载业务的实例；破坏性场景应在此前隔离演练中完成。

## 出问题时怎么退

判断标准只有一个：**新版有没有启动过。** 从第一次启动新版开始，统一按可能已有新写处理。

| 出问题的时间 | 处理方法 |
| --- | --- |
| 还没切表 | 停止迁移，保留现场。确认旧版数据完整后，用原配置和旧版恢复服务；不要删除失败作业的正文或记录 |
| 已切表，但新版从未启动，且确认没有其他新写 | 使用切换记录中审核过的逆向切表步骤，核对原分享表和旧文件，再启动旧版 |
| 新版启动过，哪怕用户入口还没打开 | 重新停入口、排空、停全部新版写入；备份全部范围的当前状态及正文，完整导回旧格式，核对后用固定旧版恢复并继续写 |
| 切表命令断线，结果不明 | 保持停机，由 DBA 查询实际表名和数据状态；查清完整旧态或完整新态之后再处理，不能凭报错认定没切成功 |

**新版启动后，不能只换回旧镜像、恢复停机前 NAS，或恢复整个共享业务数据库。**
这些做法会丢掉刚产生的问答和计数，或者影响其他业务。
完整导出或旧版验读失败时，保留新数据、保持入口关闭并修复；不能为了恢复访问而丢数据。
这条回退路线必须在上线前演练成功，不能等生产出事才补脚本。

## 开放以后还要做什么

- 按约定值班观察错误率、读取不到正文、会话长时间忙碌、停止失败、重复执行、分享失败、
  数据库锁等待、响应速度和 NAS 空间。数据错乱或缺正文立即暂停相关流量并排查。
- 完成首轮全范围新备份，并在隔离环境验证能恢复和继续写；按约定频率持续执行。
- 保留旧文件、旧分享表、最终只读备份、镜像及本次日志，直到约定回退保留期结束再处理。
- 初期只报告可清理文件，不启用自动物理删除；回收能力单独验收后再启用。
- 把最终测试、迁移核对、切表记录、验收结果和故障处理存到长期审计位置，不只留在 `/tmp`。

只有“功能可用、全部历史核对通过、全范围能恢复、新数据能退回旧版、观察期指标正常”
都成立，才把本次上线标记为完成。
