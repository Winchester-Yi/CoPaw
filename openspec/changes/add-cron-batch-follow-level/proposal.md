## Why

新版批调度看板已经能在父任务上设置「关注」，但关注只有 0/1 两档，而且完全没有参与 worker 派发：同一来源、同一模型池里，关注批次和不关注批次拿 worker 的机会完全相同。运营需要一个能表达业务重要性的档位，并让它真正影响派发先后——当前有等级更高的批次时，先分配给更高等级的批次。

## What Changes

- 父任务关注从布尔改为等级：`swe_cron_job_states.batch_follow_level`（`0` 未关注，`1..5` 关注等级，数值越大越优先）。仍挂在父任务状态行，同一父任务的所有批次共享一个等级。
- Scheduler 按 `urgent` 重跑通道、关注等级降序、既有批次与成员顺序派发批次候选。共享 Worker 的批次在各自模型池内比较等级，文本批次在直派候选列表内比较等级。
- 入队时把等级快照进执行请求的 `dispatch_meta_json`；等级变更时刷新该父任务下仍在 `queued`/`dispatch_failed` 的成员，使已经在排队的批次立即按新等级排序。
- 当日失败补跑（`task_scope=followed_batch`）与招乎批调度简报的关注过滤由 `batch_followed=1` 改为 `batch_follow_level>=1`，简报正文可标注等级。
- Console 批调度看板：批次详情与列表行（右键）都能设置 0–5 等级，列表在任务名下方用黄色星标展示等级，工具栏提供「关注等级」筛选（已关注 / 未关注 / 精确等级），筛选条件下推到看板查询接口。

## Scope

明确不做：

- **不做抢占**：只调整尚未派发成员的顺序，不打断 `dispatching`/`accepted`/`running` 的执行。
- **不做饥饿保护**：不引入老化、不设分级配额。低等级批次在高峰期长期得不到 worker 是已接受的产品风险，由运营通过调级或错峰消化。
- 共享 Worker 的容量与派发按 `(source_id, provider_id, model_id)` 分池。文本批次使用直派队列，排序无需按模型分池。
- 不改变 `batch_dispatch_priority`（用户/分行优先）与批内 `dispatch_order` 的既有语义与计算方式。
- 不改变任务定义、cron 表达式、`batch_paused` / `dispatch_paused` 暂停语义、人工重跑入口和 native 自动重试策略。

## Risks

- `_batch_order()` 是每 2 秒、每个 scope 都要跑的热查询。等级必须从已冻结的 `dispatch_meta_json` 里读取，不能为此新增 `members → receipts → job_states` 关联，否则要把派发延迟压到现有查询预算之外。
- 若只做入队快照、不做改级刷新，运营改完等级会发现「进行中的批次没反应」，直接判定功能失效。
- 等级快照需要同时写入三类重跑路径（当日失败补跑、批重跑、内部再入队），漏一处会让重跑后的成员落回 0 级。
- 关注布尔列仍在本地未提交改动里、尚未部署，因此可以整体替换；但如果已经有人用布尔版本建过表，需要一次性迁移映射（`1` → 约定默认等级）。
- 变更集跨 Scheduler 调度核心、Monitor 读模型、Console 与一次 DDL，必须按顺序上线，否则会出现「前端能设级、后端不认」或「后端排序了、看板不显示」的中间态。
