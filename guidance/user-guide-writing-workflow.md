# 用户功能指南写作流程

这份文档保存本次“扫描当前 Wiki 和代码仓库，再编写环境变量使用指南”的上下文和流程。以后需要为其他主题生成开发者用户指南时，可以按这个流程复用。

## 1. 适用场景

适用于需要把某个功能主题整理成用户指南的任务，例如环境变量、MCP、Cron、Hook、Provider、Agent 配置等。

典型目标是回答：

- 这个功能能做什么。
- 用户从哪里操作。
- CLI 是否支持。
- API 怎么调用。
- 运行时会产生什么效果。
- 有哪些限制、异常和注意事项。

目标读者是使用平台的开发者，不是本项目维护人员。因此文档应从用户可感知能力出发，不按 Controller、Service、DAO、前端、后端来分类。

## 2. 推荐保存位置

如果是某个主题的最终用户指南，建议放在 `guidance/` 下，例如：

```text
guidance/environment-variables-user-guide.md
```

如果后续要纳入正式 Wiki，再根据主题迁移到 `wiki/<topic>/README.md`。

这份流程文档本身也放在 `guidance/`，原因是：

- 它是“如何写用户指南”的参考，不是某个运行时问题的排查手册。
- `analysis/` 当前被 `.gitignore` 忽略，新建文件默认不便提交。
- `guidance/` 已经放置本次环境变量指南，后续同类产物更容易一起找到。

## 3. 写作前先确认边界

开始写之前先确认：

- 是否允许修改文件。
- 最终是写完整正文，还是只输出目录和写作方案。
- 最终写入 `guidance/`、`wiki/` 还是只在对话中输出。
- 是否需要保留调研结论。
- 最终读者是否需要看到旧文档差异。

如果是最终用户文档，通常不要写“旧 Wiki 与当前代码差异”。这类内容适合保存在调研报告或流程记录里，不适合给普通开发者用户阅读。

## 4. 扫描顺序

不要只读 Wiki。Wiki 可以作为线索，但最终以当前代码为准。

建议按这个顺序扫描：

| 类型 | 位置 | 目的 |
| -- | -- | -- |
| 后端 API | `src/swe/app/routers/`、`src/swe/app/*/router.py` | 确认路径、Method、请求模型、响应模型、错误行为 |
| 运行时逻辑 | `src/swe/` 下对应功能模块 | 确认生效时机、合并顺序、默认值、限制 |
| CLI | `src/swe/cli/` | 确认命令、参数、默认连接方式、是否调用 HTTP API |
| 前端 API | `console/src/api/` | 确认页面调用哪个接口、请求体如何构造 |
| 前端页面 | `console/src/pages/`、`console/src/layouts/` | 确认用户实际能看到和操作什么 |
| 测试 | `tests/` | 确认边界行为、异常、回归保护 |
| Wiki | `wiki/` | 查旧说明、示例和可能的功能线索 |
| README / 配置示例 | `README*`、配置目录、示例目录 | 补充用户可复用示例 |

搜索关键词应覆盖用户概念和实现概念。比如环境变量主题要同时搜：

```text
env
environment
environment variable
os.environ
getenv
stdio
mcp
header
headers
shell
subprocess
source
default env
```

## 5. 必须追踪真实实现

找到入口后继续追踪实际行为：

- Router 是否真的挂到了 `/api` 前缀。
- 请求体字段是否来自 Pydantic / TypeScript 类型。
- 返回值是否明文、脱敏或省略字段。
- 前端保存按钮实际调用 `PUT`、`PATCH` 还是 `DELETE`。
- CLI 命令是否直接写文件，还是调用 HTTP API。
- CLI 参数是否真的存在，不能沿用旧示例。
- 运行时是在进程启动时注入，还是每次调用动态解析。
- 变量引用语法是否来自代码正则或解析函数。
- 测试是否覆盖了冲突、缺省值、错误、脱敏等边界。

无法从代码确认的内容不要写成确定结论。

## 6. 用户能力整理模板

每个功能点建议先整理这些问题：

- 用户可以做什么。
- 前端入口是什么。
- CLI 是否支持。
- API 是什么。
- 请求关键参数是什么。
- 返回字段是什么。
- 实际行为是增量、全量覆盖、单项删除还是其他语义。
- 修改后什么时候生效。
- 异常时用户会看到什么。
- 哪些内部概念不应该暴露给用户。

组织方式应按用户目标分类，例如：

```text
# 功能名称

## 1. 管理功能
### 查询
### 新增和更新
### 删除
### 管理端或集成场景

## 2. 在运行时使用
### 场景一
### 场景二
### 常见问题

## 3. 默认值和限制

## 4. 完整使用示例

## 5. FAQ
```

界面、CLI、API 应合并到同一个用户目标下介绍。例如“查询”下面同时写界面、CLI、API，不要拆成“前端环境变量”和“环境变量 API”。

## 7. API 说明格式

API 统一使用这个格式：

```text
### 接口

`METHOD /path`

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
| -- | -- | -- | -- |

### 请求示例

### 返回示例

### 说明
```

如果响应对象包含大量统一平台字段，可以省略无关字段，但不能改写核心字段名。

## 8. 示例要求

示例必须来自真实实现：

- CLI 示例必须使用当前代码实际支持的参数。
- API 示例必须匹配当前 Schema。
- MCP、Header、Shell 等配置示例必须匹配当前配置模型。
- 变量引用语法必须从代码确认，不能猜 `${TOKEN}` 或 `{{TOKEN}}`。
- 默认变量表只列用户真正能感知和使用的变量。
- 如果同一个功能支持界面、CLI、API，示例要覆盖最常用路径。

## 9. 排除内容

最终用户文档不要暴露这些内容：

- 内部 scope 解析过程。
- Tenant Scoped API 这类内部命名。
- 数据库存储结构。
- DAO、Mapper、Service 调用链。
- 私有 helper 函数名。
- 内部文件路径和 secret 文件落盘路径，除非用户需要直接操作。
- 测试文件名和源码行号。
- “旧 Wiki 与代码差异”这类维护者视角说明，除非用户明确要求保留调研报告。

## 10. 自检清单

写完后至少检查：

- API 路径和 Method 是否正确。
- 请求字段名是否与代码一致。
- 返回字段是否与代码一致。
- CLI 参数是否与当前命令定义一致。
- 前端页面支持的操作是否没有夸大。
- 增量更新和全量覆盖语义是否说清楚。
- 删除行为是单 Key、批量还是整体删除。
- 修改后生效时机是否有代码依据。
- 默认变量和用户变量是否区分清楚。
- 变量引用语法是否与代码一致。
- 不存在变量时的行为是否有代码依据。
- 是否混入内部实现概念。
- 是否保留了用户不需要看的旧文档差异说明。

## 11. 本次环境变量指南的经验

这次写环境变量指南时，实际踩到的关键点：

- 先查 `/wiki` 可以快速找到旧接口和旧描述，但最终必须回到当前代码和测试确认。
- CLI 行为会随分支更新变化，不能沿用旧稿。本次 `swe env` 曾从显式 `--tenant-id` / `--source-id` 更新为读取 `SWE_TENANT_ID` / `SWE_SOURCE_ID`。
- 普通 HTTP CRUD 接口返回明文，而管理端目标写入返回脱敏值；这类细节必须从响应构造和测试确认。
- `PATCH` 的 `preserve` 字段虽然存在于 Schema，但当前代码不使用它；文档应写真实语义，而不是字段名暗示的语义。
- 最终用户文档里不要保留“旧 Wiki 差异”说明，维护者调研结论可以放在独立调研记录或流程文档中。
